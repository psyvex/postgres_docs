      content: `import {
  Injectable,
  NestInterceptor,
  ExecutionContext,
  CallHandler,
} from '@nestjs/common';
import { DataSource } from 'typeorm';
import { AuthService } from './auth.service';

/**
 * Interceptor that sets the Postgres RLS session variables before every
 * request handler runs, using the verified identity from AuthService.
 *
 * Runs BEFORE the controller method. NestJS guarantees that the same
 * DataSource instance is reused for the duration of the request, so
 * every query sees the same RLS context.
 */
@Injectable()
export class RlsInterceptor implements NestInterceptor {
  constructor(
    private readonly dataSource: DataSource,
    private readonly auth: AuthService,   // per-request instance
  ) {}

  async intercept(ctx: ExecutionContext, next: CallHandler) {
    const orgId     = this.auth.getOrgId();
    const memberId  = this.auth.getMemberId();

    if (orgId !== null && memberId !== null) {
      // set_config(...) is transaction-local: the setting disappears
      // at COMMIT, preventing a forgotten setting from leaking across
      // requests. The third argument 'true' is what makes it local.
      await this.dataSource.query(\`
        SELECT set_config('app.org_id', $1, true),
               set_config('app.member_id', $2, true)
      \`, [String(orgId), String(memberId)]);
    }

    return next.handle();
  }
}`

## How it fits together

Every request to `/tasks/*` hits three layers in sequence:

1. **JwtAuthGuard** — rejects unauthenticated requests before they touch the database. RLS is not an authentication mechanism; it assumes you already know *who* the user is.
2. **RlsInterceptor** — runs before the controller. Calls `set_config('app.org_id', $1, true)` and `set_config('app.member_id', $2, true)` on the pooled connection. The `true` argument makes the setting transaction-local: it vanishes at `COMMIT`.
3. **Controller + Service** — queries run with `SELECT * FROM tasks` and Postgres automatically filters to `WHERE org_id = $session_org_id`.

Because NestJS injects `AuthService` with `Scope.REQUEST` into `RlsInterceptor`, each request gets its own `AuthService` instance tied to its own JWT payload. The Postgres session variables are set on *that* request's connection and nobody else's.

## The SQL behind it

The lab's database already holds the same three tables your NestJS app would own —
`organizations`, `members`, `tasks` — plus the `app_member` role and the
`current_org_id()` helper. What it does *not* do is create the policies: that is
your app's migration, exactly the `001_create_schema.sql` file above. Run these in
order to watch the interceptor's contract take effect.

**Step 1 — attach the policies.** As the table owner (Superuser), once:

<SqlBlock title="One-time DDL: enable RLS + four tenant policies" sql={`ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS tenant_select ON tasks;
DROP POLICY IF EXISTS tenant_insert ON tasks;
DROP POLICY IF EXISTS tenant_update ON tasks;
DROP POLICY IF EXISTS tenant_delete ON tasks;

CREATE POLICY tenant_select ON tasks
  FOR SELECT TO app_member
  USING (org_id = current_org_id());

CREATE POLICY tenant_insert ON tasks
  FOR INSERT TO app_member
  WITH CHECK (org_id = current_org_id());

CREATE POLICY tenant_update ON tasks
  FOR UPDATE TO app_member
  USING (org_id = current_org_id())
  WITH CHECK (org_id = current_org_id());

CREATE POLICY tenant_delete ON tasks
  FOR DELETE TO app_member
  USING (org_id = current_org_id());`} expect="RLS on, four policies owned by the superuser — the app role can neither add nor drop them." />

**Step 2 — the app queries with no WHERE clause.** These blocks run as the
personas, so each one is exactly one HTTP request through
`RlsInterceptor` → controller → `repo.find()`:

<SqlBlock title="Alice's request — plain SELECT, no filter" as="alice" sql={`SELECT t.id, t.title, o.name AS org

<SqlBlock title="Carol's request — different JWT, different rows" as="carol" sql={`SELECT t.id, t.title, o.name AS org
FROM tasks t

**Step 3 — a bug in the app can no longer leak data.** Suppose a junior dev
forgets to scope an insert, or a compromised client sends the wrong org:

<SqlBlock title="Alice's request tries to write into Carol's org" as="alice" sql={`INSERT INTO tasks (org_id, project_id, title, status)
  VALUES (2, 3, 'Trying to spy on Globex', 'todo')
  RETURNING id, title, org_id;`} expect="ERROR: new row violates row-level security policy — WITH CHECK rejects the write." assert={[{error: 'row-level security'}]} />

The `org_id = 2` in that statement came from the *request body*, which the policy
never trusts. `WITH CHECK` compares the new row against `current_org_id()` —
which only the interceptor, reading a verified JWT, is allowed to set.

## Two rules you must never break

<Callout type="warn" title="Rule 1 — never let the app connect as superuser">

Your NestJS app must connect as a *dedicated application role* (`nest_app`), not as `postgres`. The superuser bypasses RLS, which defeats the entire point. Create the app role with only `GRANT SELECT, INSERT, UPDATE, DELETE` on tables — no `SUPERUSER`, no `CREATEROLE`, no `BYPASSRLS`.

```sql
CREATE ROLE nest_app NOLOGIN;
GRANT CONNECT ON DATABASE app_db TO nest_app;
GRANT USAGE, SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO nest_app;
```

</Callout>

<Callout type="danger" title="Rule 2 — set identity server-side, never from the client">

The `set_config` call in `RlsInterceptor` reads from a *verified* JWT payload. Never derive the org_id from a request header the client can set:

```typescript
// WRONG — client controls the header
const orgId = request.headers['x-org-id'];

// RIGHT — identity comes from the verified token
const orgId = this.verifyJwt(token).orgId;
```

An attacker who controls the RLS context can read any tenant's rows.

</Callout>

## What the interceptor looks like without NestJS

If you are not using NestJS, the same pattern works in any framework. The principle is identical:

```typescript
// Express example (same idea, no DI container)
app.use(async (req, res, next) => {
  if (req.user) {
    await pool.query(
      `SELECT set_config('app.org_id', $1, true), set_config('app.member_id', $2, true)`,
      [String(req.user.orgId), String(req.user.memberId)],
    );
  }
  next();
});
```

With PgBouncer in **transaction mode** this works without changes: each request borrows a connection, sets the RLS context, runs queries, and returns the connection. The setting is cleaned up automatically when PgBouncer resets the connection for the next transaction.

## Recap

| Piece | What it does |
|---|---|
| `Scope.REQUEST` `AuthService` | Holds verified identity for this request only |
| `RlsInterceptor` | Sets `app.org_id` and `app.member_id` on the Postgres session |
| `set_config(..., true)` | Transaction-local — vanishes at COMMIT |
| `FORCE ROW LEVEL SECURITY` | RLS applies even to the table owner |
| `JwtAuthGuard` | Stops unauthenticated requests *before* RLS context is set |
| `nest_app` role | App connects with least privilege; does not own tables |
