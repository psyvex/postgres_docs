- **A lesson on partitioning, where the plan is the proof** (`src/content/topics/partitioning.mdx`, registry `status: 'ready'`, 18 min, Performance track, 5 references). The app had taught indexes, plans and MVCC, and a reader who has ever been told "just partition the table" had nowhere to look. It builds a 12-partition range-partitioned `events_p` over 120,000 rows and then proves each claim with `EXPLAIN (COSTS OFF)`: `pg_table_size` of the parent is **0 bytes** against June's **848 kB** (the parent is a routing header), `tableoid::regclass` on `RETURNING` shows which drawer a row landed in, `FROM ONLY events_p` counts **0** while `FROM events_p` counts **120,001** — the distinction that trips people writing archive queries. Pruning is shown three ways and once in reverse: one day → `Aggregate → Seq Scan on events_p_2024_06` with **no Append node at all**; `>= 2024-11-01` → Append over November and December; no predicate → Append over all twelve; then `SET enable_partition_pruning = off` putting every partition back with a `Filter:` on each, which is the only way to see what the planner was quietly saving. One `CREATE INDEX` on the parent becomes twelve physical indexes (proved by listing `pg_class` for one partition: the table and `events_p_2024_06_user_id_idx`), and the composite plan is a `Bitmap Index Scan` into exactly one partition. The constraint rule is taught through its error — `CREATE TABLE … (id int PRIMARY KEY) PARTITION BY RANGE (created_at)` → **unique constraint on partitioned table must include all partitioning columns** — and fixed by putting `created_at` in the key. The `DEFAULT` partition gets the section it deserves: it catches a 2023 row (`tableoid` → `events_p_default`), and it *changes the pruning answer*, because an unbounded partition cannot be proved empty, so `>= 2024-11-01` goes from two scans to three. `DETACH` leaves a standalone table of **10,198** January rows and a parent that now counts **109,804**. Hash partitioning is shown doing its job (`= 42` opens exactly `visits_2`, because 42 mod 4 = 2) and not doing it (`> 42` opens all four), with the measured uneven bucket split **259/234/276/231** for 1,000 rows; list partitioning ends with the only operation that moves a row between tables — an `UPDATE` to `region`. Cheat sheet, `pg_get_partition_constraintdef` and `pg_partition_tree` reference blocks (with the column list that is `relid/parentrelid/isleaf/level` — there is no `depth`), and 6 questions. A Callout states plainly that `pg_stat_user_tables.n_live_tup` reads **0** for every table here, because PGlite runs no background workers, and the lesson uses `count(*)` instead of pretending.

(`src/content/topics/transactions-mvcc.mdx`, registry `status: 'ready'`, 22 min, Foundations track, 6 references). The security lessons keep saying "Postgres never overwrites a row" and the indexes lesson keeps saying "the plan is about visibility", and until now nothing in the lab showed the mechanism that makes both true. The lesson builds a 20,000-row `orders` table and then reads the database's own diary: `xmin`/`xmax` on live rows, the `function min(xid) does not exist` error that forces the honest `xmin::text::bigint` cast (and the `xid8` type that exists because xids are a 32-bit counter that wraps), a `DELETE` after which `SELECT count(*)` says 0 and `pg_stat_user_tables.n_dead_tup` says **1** — the row is a retirement, not an erasure. Then the abstraction you can print: `pg_current_snapshot()` → `755:755:`, decoded into xmin/xmax/xip, and `backend_xmin IS NOT NULL` measured from inside a `BEGIN`, which is the mechanism behind the most common production vacuum incident (one forgotten `BEGIN;` in a psql session, left open for a day, holds the horizon back and the table inflates). The isolation levels get what they actually promise, demonstrated: `SHOW transaction_isolation`, `SERIALIZABLE, READ ONLY` refusing an `UPDATE` outright, and `REPEATABLE READ` showing your own uncommitted write — with a Callout naming the thing the lab *cannot* show, which is the difference between the levels, because that difference is about **other sessions** and the browser has exactly one connection. Atomicity and savepoints (`ROLLBACK TO` keeps the first insert, a mid-batch error discards all of it), locks as rows you got to first (`FOR UPDATE` → 1 `RowShareLock`, `COMMIT` → 0; advisory locks **reference-counted**, so two `pg_try_advisory_lock(42)` need two unlocks or the token leaks for the life of the connection), and bloat measured rather than asserted: 5,000 non-HOT updates grow the heap *and* the index (2,176 kB / 192 kB), then `fillfactor = 70` + 5,000 inserts + 5,000 updates on an unindexed column grow the heap and leave the index at 240 kB — `n_tup_upd 10,001`, `n_tup_hot_upd 3,523`, **35.2 % HOT**, and **118 bytes per live row** against a row that costs about 70, which is the number to quote in a review. `VACUUM` fails with "cannot run inside a transaction block" — so the lesson makes that the subject of a section, contrasts `REINDEX`/`ANALYZE`, which run fine, and names why `autovacuum_count` stays 0 here (PGlite has no background workers). Ends with a cheat sheet, a two-`psql`-window script for the experiment one connection cannot run, and 6 questions.

- **No `affected: n` assertion could ever pass in CI.** `scripts/verify-lessons.mjs` built its `RunResult` with `rowCount: r.rows.length`, and a DML statement that returns no table has zero rows — so the grader's `affected` channel read 0 in CI for every block, while the same block passed in the browser, where `local-adapter.ts` derives the count from `affectedRows`. The lesson this is evidence for: the verifier is a *second implementation* of the app's result-shaping, so every app-side rule has to be mirrored deliberately, and a divergence shows up as a check that can only fail in one of the two places.

It meters **only a stream the caller already owns** — the server path hands over the one `MediaRecorder` is recording, so one `getUserMedia` feeds both. Measured: server path 1 `getUserMedia`, 21 bars, trail `0.12 → 0.51 → 0.49` (button ring `1.06 → 1.24`), 2 tracks stopped on stop; browser path 0 `getUserMedia`. The level uses a saturating curve (`1 − e^(−rms·4.2)`) rather than a linear clamp, because a linear one pins every bar at full height the moment someone speaks loudly, and a solid wall of bars shows no spikes. The first measurement read a flat `0.1` because an `AnalyserNode` is not a sink — a graph that ends in one is never pulled, so the analyser reports silence; a zero-gain `GainNode` tail into `ctx.destination` keeps the graph running and stays inaudible.
